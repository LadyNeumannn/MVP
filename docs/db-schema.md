# Схема БД

PostgreSQL, 4 таблицы + 1 enum-тип. Миграции: `migrations/0001_init.{up,down}.sql`.

## restaurants
Заведения, подключённые к площадке.

| Колонка       | Тип         | Описание                                   |
|---------------|-------------|---------------------------------------------|
| id            | UUID PK     | генерируется приложением                    |
| name          | TEXT        | название заведения                          |
| is_active     | BOOLEAN     | принимает ли заведение заказы сейчас        |
| webhook_url   | TEXT        | куда слать уведомления о новых заказах      |
| api_key       | TEXT        | персональный ключ заведения для Partner API (миграция 0004); хранится в открытом виде — осознанное MVP-упрощение, см. README |
| created_at    | TIMESTAMPTZ |                                              |

## menu_items
Позиции меню, привязаны к заведению.

| Колонка       | Тип         | Описание                                   |
|---------------|-------------|---------------------------------------------|
| id            | UUID PK     |                                              |
| restaurant_id | UUID FK     | -> restaurants.id, ON DELETE CASCADE        |
| name          | TEXT        |                                              |
| description   | TEXT        |                                              |
| price_cents   | BIGINT      | цена в копейках, чтобы избежать float       |
| available     | BOOLEAN     | доступна ли позиция для заказа сейчас       |
| created_at / updated_at | TIMESTAMPTZ | |

Индекс `idx_menu_items_restaurant` это быстрая выборка меню по заведению
(основной паттерн доступа: и клиентское, и партнёрское API читают меню
целиком по `restaurant_id`).

## orders
Заказ пользователя.

| Колонка       | Тип          | Описание                                  |
|---------------|--------------|---------------------------------------------|
| id            | UUID PK      |                                              |
| restaurant_id | UUID FK      | -> restaurants.id                           |
| customer_name | TEXT         | без авторизации — просто имя из формы       |
| customer_phone | TEXT        | контактный телефон для курьера (добавлено миграцией 0003) |
| delivery_address | TEXT     | адрес доставки, свободный текст, без геокодирования (миграция 0003) |
| status        | order_status | enum: created/confirmed/preparing/ready/delivered/cancelled |
| total_cents   | BIGINT       | сумма, посчитанная на момент создания       |
| created_at / updated_at | TIMESTAMPTZ | |

Индекс `idx_orders_restaurant_status` под самый частый запрос
партнёрского API: "мои заказы в статусе чего-то там".

## order_items
Состав заказа, со снапшотом цены и названия на момент покупки.

| Колонка               | Тип     | Описание                                  |
|------------------------|---------|---------------------------------------------|
| id                     | UUID PK |                                              |
| order_id               | UUID FK | -> orders.id, ON DELETE CASCADE             |
| menu_item_id           | UUID FK | -> menu_items.id (для трассировки к позиции)|
| name_snapshot          | TEXT    | название на момент заказа                   |
| price_cents_snapshot   | BIGINT  | цена на момент заказа                       |
| quantity               | INT     | > 0                                          |

**Почему снапшот, а не просто ссылка на `menu_items`:** цена и название
позиции могут поменяться после того, как заказ уже оформлен (заведение
поправило меню). Уже созданный заказ не должен "поплыть" — поэтому на
момент оформления заказа мы копируем `name`/`price_cents` в `order_items`.
Это осознанное упрощение модели, которое одновременно снимает и часть
проблем консистентности при масштабировании (заказ самодостаточен и не
требует джойна с текущим состоянием меню, чтобы показать, что купил
пользователь).

## webhook_outbox
Transactional outbox для доставки уведомлений заведениям о новых заказах.

| Колонка         | Тип         | Описание                                  |
|-----------------|-------------|---------------------------------------------|
| id              | UUID PK     |                                              |
| order_id        | UUID FK     | -> orders.id, ON DELETE CASCADE             |
| webhook_url     | TEXT        | куда слать (снапшот на момент заказа)       |
| payload         | JSONB       | сериализованный заказ (domain.Order)        |
| status          | TEXT        | pending / delivered / failed                |
| attempts        | INT         | сколько раз пытались доставить              |
| last_error      | TEXT        | текст последней ошибки, если была           |
| next_attempt_at | TIMESTAMPTZ | когда можно пробовать снова (backoff/лиз)   |

**Зачем отдельная таблица, а не просто "отправить и забыть":** запись
сюда происходит в той же транзакции, что и сам заказ (см. `CreateOrder`
в `postgres.go`) значит, событие durable в БД с момента коммита
заказа и переживает падение процесса `kuhnya`. Раньше уведомление
слалось напрямую из горутины сразу после коммита, при падении
процесса между коммитом и отправкой оно терялось молча. Отдельный
воркер (`internal/service/outbox_worker.go`) вычитывает `pending`
записи и доставляет их с экспоненциальным backoff.

## Что не сделано в MVP и как масштабировать дальше
- Нет таблицы `users`, авторизация вне скоупа задания.
- `restaurant_id` в `orders`/`menu_items` что в
  реальности упростит шардирование по заведению (частый паттерн для
  маркетплейсов: заведение естественная единица шардирования).
- При росте нагрузки на чтение меню лучше использовать кэш (Redis) поверх
  `GET /menu`, т.к. меню меняется значительно реже, чем читается.
- Поиск (`GET /restaurants?q=`, `GET /menu?q=`) сейчас это `ILIKE
  '%...%'` без индекса: при малом объёме MVP это ок, но `ILIKE` с
  ведущим `%` не может использовать обычный B-tree индекс. При росте
  данных нужно `pg_trgm` + GIN-индекс на `name`, либо полноценный
  full-text/поисковый движок (Elasticsearch/Meilisearch), если нужна
  релевантность, а не только подстрока.
- `delivery_address`/`customer_phone` добавлены отдельной миграцией
  `0003_delivery_info.up.sql`, а не правкой `0001_init.up.sql`, поэтому уже
  применённые миграции принципиально не переписываются задним числом,
  только новые поверх. На уже поднятом контейнере с volume `pgdata`
  эта миграция не подхватится автоматически (docker-entrypoint-initdb.d
  выполняется только при первой инициализации тома), так что нужен либо
  `docker compose down -v` + новый `up`, либо ручное применение.
